On Linux and macOS, Nodecode runs the agent in a jail by default. Read what it stops and what it doesn't before you connect a channel or run unattended.

{/* source: src/gateway/sandbox.lisp */}
## The jail

The jail holds the agent: every `eval`, every shell command it runs, every cell, and the background gateway. The terminal you type in stays outside it.

| What | Inside the jail |
| --- | --- |
| Files | The project folder you started in, read and write. Its own `~/.nodecode`, read and write, except the files below. The system, read-only. |
| Your home | Not there: `~/.ssh`, `~/.aws`, `~/.gnupg`, browser profiles, other agents' homes. Neither is the host's `/tmp`. |
| Keys and sign-ins | Not there: `auth.json` and `secrets/` are left out. Nodecode's proxy adds a key or sign-in token to each request bound for its own provider. |
| Network | Only through the proxy, to the hosts it allows: your providers, nodecode.ai, models.dev, GitHub, and the chat services you configured. Any other host is refused. |
| Local sockets | None of the host's: no Docker socket, no display, no desktop bus, no tmux server. |
| `config.jsonc`, `sandbox.jsonc` | Read-only. The agent can't widen its own jail. |

Started in your home folder or above it, a shell holds no folder: a jail around the whole home would hold nothing back. It writes only its own `~/.nodecode` and the folders you allowed, so `cd` into a project first. `nodecode serve` and the background gateway hold no folder of their own either: their home and the folders you allowed.

| Command | What it does |
| --- | --- |
| `nodecode sandbox status` | Shows the folders and hosts the jail allows. |
| `nodecode sandbox allow PATH` | Adds a folder, read-only. `--write` makes it writable. Kept in `sandbox.jsonc`. |
| `nodecode sandbox allow HOST` | Adds a host to the proxy's list. |
| `nodecode sandbox revoke PATH` | Takes a folder back out. |
| `nodecode sandbox off` | Turns the jail off for this home, after asking. `nodecode sandbox on` turns it back on. |
| `nodecode --no-sandbox` | Asks the same as `sandbox off` and keeps the answer. With no terminal to ask on, it refuses. |

| System | Jail |
| --- | --- |
| Linux | bubblewrap (`bwrap`), which Fedora and Ubuntu desktops ship. Without it Nodecode doesn't start, and says how to install it or turn the jail off. |
| macOS | The system sandbox, `sandbox-exec`, with a profile Nodecode writes. The keychain, `sudo` and other setuid programs are refused too. |
| Windows | None yet. Nodecode runs with your account's full access and says so at every launch. |

A home the jail ran is marked. A launch without the jail refuses until you have read `nodecode sandbox review`, which lists what the jailed agent wrote that would run outside it: the layer and the cells.

## What the jail doesn't stop

| Fact | Consequence |
| --- | --- |
| The project folder is the agent's to change. | Keep it in git. `/undo` restores what a turn changed there. |
| Allowed hosts are reachable. | The agent can send what it reads in the folder to them, GitHub included. |
| Channel messages give the agent work. | Anyone on a bot's allowlist can make it run commands inside the jail. A bot's token is in the jail, so a prompt injection could post as that bot. |
| Cells are code. | A cell runs inside the jail with the agent's access. A hub cell is someone else's code: read it first. |
| The guard is not a security boundary. | It refuses known spellings of risky commands. Any other spelling runs, inside the jail. |
| Without the jail, eval has your account's authority. | `--no-sandbox`, `sandbox off` and Windows: the model can read, write and run anything your user can, `auth.json` and `secrets/` included. |

## Protections around it

| Protection | What it does |
| --- | --- |
| Loopback gateway | The gateway, the local server shells attach to, listens on `127.0.0.1`. |
| Host check | A request whose `Host` is not `127.0.0.1` or `localhost` gets 403. |
| Origin check | A socket opened by a page of another origin gets 403. |
| Operator token | Every `/api/gateway/` route needs `Authorization: Bearer TOKEN`. `/healthz` needs none. A jailed gateway gets a token made for that launch. |
| Cell routes | A route a cell serves on the gateway's port needs the same token, unless the cell marks it public: a browser page, a webhook, a sign-in callback. A public route is responsible for its own checks. |
| File modes | Secrets are readable by you alone. See the table below. |
| Kernel lock | The kernel, the locked core, refuses redefinition of its names. The model can lower it with `lower-floor`; the store records who asked and why. It is not a security boundary: the jail is. |
| Secret redaction | `config-get` shows a secret as `[set]`. `config-set` refuses to write `[set]` back. |
| Channel allowlists | A Discord, Slack or Telegram bot refuses to start without an allowlist. |
| Channel tokens | A bot token is named by a `*_env` or `*_file` key. Inline tokens are not read. |

| Token source | Order |
| --- | --- |
| `NODECODE_GATEWAY_OPERATOR_TOKEN`, then `NODECODE_OPERATOR_TOKEN` | 1 |
| `~/.nodecode/operator-token`: 32 random bytes as hex, made on first boot | 2 |
| `gateway.operator_token` in the config | 3 |

`nodecode web` prints a link that carries the token after `#`. A browser never sends that part to a server. Keep the link to yourself.

| Path | Mode |
| --- | --- |
| `~/.nodecode/` | 0700, set when the store opens |
| `operator-token`, `auth.json`, files in `secrets/`, `link/state.json` | 0600 |
| `backups/` | 0700. Each archive: 0600. |
| `snapshots/` | 0700, and each snapshot's program: it holds your keys. Each manifest: 0600. |
| `config.jsonc` | No mode is forced. A write keeps the mode the file has. |

## Updates

Nodecode checks nodecode.ai for a new release. A release is a tarball fetched over HTTPS and checked against its sha256 before it is staged. Releases are not signed yet.

| `update.mode` | What happens |
| --- | --- |
| `auto` | The release is applied in the running process. What can't change live lands at the next launch. |
| `ask` | The release is staged, and waits for `nodecode update`. |
| `off` | Nodecode never looks. |

`nodecode update VERSION` goes back to a release and holds there.

## Safe baseline

1. Keep the jail on. Start Nodecode in the project folder it should work on.
2. Keep the project in git.
3. Give every channel an allowlist of users, channels or chats, and keep `require_mention` on.
4. Name channel tokens with `*_env` or `*_file`.
5. Keep the `nodecode web` link and the `operator-token` file private.
6. Install cells only from sources you trust. Read the code first.
7. Set `update.mode` to `ask` if you want to read each release before it applies.
8. Turn the background gateway off when you don't need it: `/settings` > System > Gateway, or `nodecode gateway off`. It comes back at every login, and runs in the jail.
9. On Windows, until the jail ships there, run Nodecode in a VM or under a separate account before you leave it working alone.
