The gateway is the local server that shells attach to. The background gateway keeps it and the organism, a running Nodecode, up with no shell open.

{/* source: src/gateway/background.lisp */}
## Verbs

```sh
nodecode gateway
nodecode gateway on
nodecode gateway off
nodecode gateway restart
nodecode gateway logs --follow
```

| Verb | Does |
| --- | --- |
| none, `status` | Prints the state: off, serving, waiting, starting, stopped, restarting, failed or unavailable. |
| `on` | Writes the unit. Enables it. Starts it. On Linux, asks logind to keep it running after logout. |
| `off` | Disables the unit, removes its file and stops the process. Writes `gateway-off`. Refused from inside the gateway, see below. |
| `off --force` | The same, from inside the gateway too. |
| `restart` | Restarts on the current build with the current config. Refused while the gateway is off, and from inside it. |
| `restart --force` | The same, from inside the gateway too. |
| `logs` | Prints the last 60 log lines. |
| `logs --follow`, `logs -f` | Keeps printing new lines. Command line only. |
| `run` | Runs the gateway in the foreground. This is what the unit runs. Command line only. |
| `help [VERB]` | Prints help. |

`/gateway` does the same from a shell, its verbs as rows: where it stands, on, a restart, off, its log, and setting up Discord, Telegram or Slack. A shell is the terminal UI. `/settings` > System > Gateway > Run in the background turns it on or off: Off is `off`, and writes `gateway-off`. On is `on`.

For a profile, add `-p NAME`:

```sh
nodecode -p NAME gateway on
```

While it serves, the status adds the pid, the port, the uptime and the build. It also says whether the gateway starts at login, and lists the standing notices of cells.

## What on installs

| Platform | Installs | Unit file |
| --- | --- | --- |
| Linux | A systemd user unit | `~/.config/systemd/user/nodecode-gateway.service` |
| macOS | A LaunchAgent | `~/Library/LaunchAgents/nodecode-gateway.plist` |
| Windows | Nothing | None |

Windows: no background gateway. `status`, `on`, `restart` and `logs` say so. Run `nodecode serve` in a terminal you keep open.

On Linux the unit folder follows `XDG_CONFIG_HOME` when it is set.

| Home | Unit name |
| --- | --- |
| `~/.nodecode/` | `nodecode-gateway` |
| A profile | `nodecode-gateway-NAME` |
| Another `NODECODE_HOME` | `nodecode-gateway-` plus 8 hex digits of the path's hash |
| Any home under a `HOME` that is not your account's own | The same hashed name |

The home is `~/.nodecode/` unless a profile or `NODECODE_HOME` names another. Your account's own home is the one the system's user database names. A link to it counts. A scratch `HOME` never takes the account's `nodecode-gateway`.

| Setting | Linux | macOS |
| --- | --- | --- |
| Runs | `nodecode gateway run` | The same, through a launcher |
| Restart after any exit | After 5 s | Yes, at most once per 5 s |
| Watchdog | 30 s | None |
| Stop timeout | 60 s | 60 s |
| Log | The user journal | `~/Library/Logs/nodecode/nodecode-gateway.log` |

On macOS the launcher is copied once to `~/Library/Application Support/nodecode/launcher/1/nodecode`.

`on` refuses to overwrite a unit file of that name that Nodecode did not write. `off` leaves such a file alone.

## Shells and the gateway

| Situation | Result |
| --- | --- |
| A shell owns the store, then the gateway starts | The gateway waits. It takes the organism over when that shell closes. |
| The gateway serves, then a shell opens | The shell attaches. Its footer shows `Gateway`, colored by the connection. A click opens the web page on Sessions. |
| The gateway restarts: for an update, or after a clean exit | Open shells wait up to 60 s for it to take the store again, then attach. Meanwhile they start no organism of their own. |
| Turned off in `/gateway`, from an attached shell | The gateway stops. That shell takes the organism over. |

See [The organism](organism.mdx).

## Logout

| Platform | Behaviour |
| --- | --- |
| Linux, linger on | The gateway starts at boot. It keeps running after logout. |
| Linux, linger off | The gateway starts at login. It stops at logout. |
| macOS | The agent starts at login. It stops at logout. launchd has no linger. |

`on` runs `loginctl enable-linger` for your account. If your system refuses, the status says so. Then run once:

```sh
sudo loginctl enable-linger $USER
```

Run the same command when the status says systemd has no user manager.

## Automatic start

The organism turns the gateway on at the first boot of `~/.nodecode/` or a named profile, when `HOME` is your account's own home. Any other home is left to you, or to a cell.

A cell is a folder of code under `~/.nodecode/cells/`. Four cells also turn the gateway on by themselves:

| Cell | When |
| --- | --- |
| Channels | A bot starts. |
| Cron | A job is scheduled, or active jobs exist at start. |
| Link | The link is on. |
| Prs | The pull request watch starts. |

Every attached shell shows a notice when this happens. The organism's says `nodecode's gateway keeps your sessions running after this shell closes, and comes up at every login · /settings turns it off`.

Nothing turns the gateway on by itself in these cases:

- `~/.nodecode/gateway-off` exists.
- The organism runs with `--ephemeral`.
- The platform is Windows.

## From inside the gateway

A process the gateway started inherits its `NODECODE_HOME`: an agent's tool shell, a script that shell runs, a tmux session it leaves behind. On Linux that is every process in the unit's control group. There `nodecode gateway off` and `nodecode gateway restart` are refused, because stopping the gateway would end the process part way.

The refusal names the unit and its home, and nothing is changed. A script meant for another home sets `NODECODE_HOME` first. `--force` stops or restarts the gateway anyway. The gateway's own web page and the installer always force.

## gateway-off

`nodecode gateway off` writes the file `~/.nodecode/gateway-off`.

While the file exists, neither the organism nor a cell turns the gateway on. Bots and cron jobs then run only while a shell is open.

`nodecode gateway on` deletes the file.

## Updates

The unit names the installer's `current` link. A restart runs the build installed last.

| Event | Result |
| --- | --- |
| The installer finishes, gateway running | The installer runs `nodecode gateway restart` for it. |
| The installer finishes, gateway stopped | Nothing. The next start runs the new build. |
| `nodecode update` needs a restart | The organism restarts itself through the unit at an idle moment. |
| `nodecode gateway restart` | Rewrites the unit first if the binary path or `PATH` changed. |

The installer restarts only units that Nodecode wrote. See [Updates](updates.mdx).

## Stopping work

Escape, and `(eval-interrupt N)`, ask the owned work to stop. They do not kill its thread. A wait that registered a waker is woken, returns, and then the turn closes.

Socket cancellation is ownership-scoped, including provider stream reads. Returning a connection to the pool retires it from every enclosing wait before another caller can borrow it. A cancellation arriving before a new socket is registered is remembered and wakes that socket when registration completes. Neither path asynchronously unwinds its worker.

| What you did | What you see |
| --- | --- |
| Escape during a provider stream | The socket is shut down (`SHUT_RDWR`, not closed from another thread). The read returns. The turn closes as cancelled. Measured on a local provider that sent one delta and then held the socket silent: 69 ms from Escape to `turn.cancelled`. |
| Escape during a shell command, `(sh ...)` in an eval | Every process of the command's tree gets `SIGTERM`, then `SIGKILL` if it is still there after 0.2 s, including a command that leads a session of its own. The pipe ends, the eval exits 130 and keeps what the command wrote. The turn closes as cancelled. Measured on `sleep 30`: 77 ms to `turn.cancelled`, 98 ms until `sleep` was gone. |
| Escape during a wait the host owns (a retry pause, a parked provider stub) | That wait is notified. The turn closes as cancelled. Measured: 10 ms. |
| Escape during an eval whose form never returns, such as `(loop)` or `(loop (sleep 0.05))` | The turn closes as cancelled (45 ms for both). The eval does not stop: it keeps running in the background. `(list-evals)` still shows it `:running` 5 s and 60 s after Escape. `(loop)` keeps one core busy (1.00 s of CPU per second at 5 s and at 60 s); `(loop (sleep 0.05))` costs nearly nothing. The session takes new turns meanwhile. Only a gateway restart ends such an eval. |
| Escape during a foreign call that registered no waker, in the turn's own thread | The request is recorded. The turn stays active and the worker keeps running. One second after the request: still not `turn.cancelled`, about one core, RSS +12 KiB. Nothing restarts the gateway for you. |
| `(eval-interrupt N)`, including `:force t` | The same request. `:force` does not terminate the thread. |

A pending worker does not fail the watchdog. The gateway stays up, and other sessions keep serving. A session whose turn is stuck in such a foreign call does not take another turn until that worker returns, or until you restart. The stream, shell and eval rows were measured by pressing Escape in a real shell in a terminal, attached to its gateway, with a provider played on loopback; the host-owned wait and foreign call rows inside one image.

To clear a worker that will not return, restart the gateway yourself: `nodecode gateway restart`. That ends the whole process, including every other session. A worker that has been pending for minutes does not, by itself, mark the gateway unhealthy.

An optional escalation is not built: a worker still pending N minutes after a stop request could mark health degraded so the watchdog restarts the gateway. N is not chosen. What a restart loses is every live session, not only the stuck worker.
