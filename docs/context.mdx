Nodecode's agent manages its own context, the way a [Context Language Model](https://arxiv.org/abs/2609.37725) (Shao et al., 2026) does: the context is a file the agent may edit without restriction, and the next request reads what it left. Nothing it lets go is lost. The context is a window over a log that is never edited, and recall reads any of it back word for word.

| Part | What it does |
| --- | --- |
| [Working context](#working-context) | The agent cuts, edits, notes and restores its own context. |
| [Recall](#recall) | Reads anything that left the window back from the log. |
| [Eviction](#eviction) | The backstop: drops the oldest turns when the agent did not shrink the context in time. |

## Working context

`(context)` writes the session's context to `context.txt` and returns its path. The file sits under the home at `context/STORE/SESSION/context.txt`, one per store and session. Edit it with any file verb, a shell command or Lisp. There is no summarizing API and no size target: growing the context, cutting it, writing notes and restoring blocks are all edits.

The first line names the export and, once a round has reported it, how full the window is. Keep it. Below it, each message of the retained history is a block under a `[[m:NONCE ID ROLE]]` line, where ID is its log position. A tool block's first line is its call, and the rest is its result. Harness lines and the active request are not in the file, and they stay where they stand.

| In the file | The next request reads |
| --- | --- |
| A block left as it is | The message as it was, byte for byte, so it stays cached. |
| A block deleted | Nothing. A tool block takes its call with it. |
| An assistant's text or a tool result edited | The edit, in the same place. An edited result ends with the recall line that reads the original. |
| A call line edited | A stand-in for the call's arguments that names the original. |
| A user ask edited, or text under a `[[note]]` line, above the first block or after a block's own text | A note: an assistant message labelled `[context note]`. It reads as the agent's own words, never as the operator's and never as a call that ran. |
| A removed block's header written back, anywhere | The original message, where it stood. |
| A block moved behind a later one | A note, where it was moved to. |

Every call stays answered. A call whose result left answers that it did.

### Edit by seq

Every tool result ends with its seq: `[seq 57]`. `(context :drop SPANS :keep IDS :note TEXT)` makes the same edit without the file.

| Keyword | Takes |
| --- | --- |
| `:drop` | `t` for every block, or a list of seqs, ids (`"n1"`, `"57c"`) and `(from . to)` spans. |
| `:keep` | Seqs held back from the drop. |
| `:note` | The agent's note, kept at the end. Alone, it changes nothing else. |

```lisp
(context :drop '(1200 . 1250) :note "deploy fixed and proved; open: the docs page")
(context :drop t :keep '(1257) :note "…")
```

The call returns what the next request will take. Calls in the same round compose.

### When an edit is taken

The next model request takes the edit, or refuses it and says why. `context.receipt.txt` says what it kept, changed, removed and added. Refused bytes go to `context.rejected.txt`. Either way the file is then written afresh, but a file still holding an edit not yet taken is never overwritten.

An edit is refused when its first line changed, when another edit was taken after the file was written, or when the session moved to another branch. Newer turns do not refuse it: a file read rounds ago still edits, and the newer turns follow it.

A taken edit is one `context.edited` event in the log. The shell shows it as one `Context` row, such as `~95k → ~41k tokens · 12 removed · 1 note · by the model`. The log itself is never edited: the edit changes what the next request reads, and recall still reads every original.

### Cache cost

Messages before the first change stay byte for byte as they were, so the provider's cached prefix holds through them. A note added at the end costs only itself. The receipt says how far the prefix holds: `the first 40 of 52 messages are unchanged, so the cached prefix holds through them`. An edit at the first message sends the history after the system prompt uncached, once.

Everything after the first change is sent again. No provider here reuses a cached suffix. Reasoning still rides the messages before the first change. From the first change on, signed reasoning is not replayed.

### Forks, resume and rewind

Each session edits its own file. A fork inherits the edit visible where it forked, and never a file. Resume rebuilds the view from the store. A rewind restores the older branch's view.

### The standing rule

The `nodecode-context` cell is built into every binary, so it runs in a pristine boot and in a home with no cells installed. It gives the agent one standing rule: edit at checkpoints, after a subproblem settles and before the final answer, in one `(context :drop …)` call. The note keeps constraints, decisions, verified state, open work and evidence pointers. Free room in the window is not the test, because every kept block rides every request. Correctness outranks size.

### Beside the paper

| Context Language Models | Nodecode |
| --- | --- |
| The context is mirrored to a file the model edits with Bash. | `context.txt`, edited with any file verb or shell command, or in one call with `(context :drop …)`. |
| An edit reaches the live context on the next turn. | An edit is taken at the next model request, and a receipt says what was taken. |
| Several agents' contexts coexist as files. | One file per session. A fork inherits the edit taken where it forked. |
| Suffix Cache Reuse keeps a middle edit cheap on the server. | The cached prefix holds up to the first change. Everything after it is sent again. |
| Instructions or reinforcement learning shape the editing policy. | The standing rule shapes it. No learned policy ships. |

## Budget

The budget is the model's context window in tokens. The first source that has a number wins.

| Order | Source |
| --- | --- |
| 1 | `NODECODE_CONTEXT_TOKENS` |
| 2 | `providers.<id>.models[].context_window` in `config.jsonc` |
| 3 | Overrides for the model recorded in the running image |
| 4 | The models.dev cache at `~/.cache/nodecode/models.dev/api.json`, or the file `NODECODE_MODELS_CATALOG` names |

A model no source knows has an unknown window.

<Note head="Unknown window">An unknown window is never proactively evicted. Eviction then starts only when the provider rejects a request as too large. Set `context_window` to give the model a budget.</Note>

Nodecode also learns the window. A request the provider rejects as too large records a ceiling for that provider and model, and that ceiling is the budget from then on. A round that succeeds records a floor, which can raise a models.dev window. A number from rows 1 to 3 is never corrected.

`/context [prompt | tools | index | notes | history | time]` shows this session's context window and usage: the newest round's prompt over the window, configured, learned or the model's own. It splits the prompt into the standing prompt, the tools, the skills and memories index, the model's notes and the history. `history` lists the turns, and Enter evicts through one. `time` charts each round's prompt from the log.

## Eviction

Eviction is the backstop for a context the agent did not shrink. It acts only at a request that is still over the line.

| Setting | Value |
| --- | --- |
| Warns at | 0.85 of the budget, once: `[context X of Y, past the 85% line: the next request evicts your oldest history unless it shrinks first. (context :drop SPANS :keep IDS :note TEXT) shrinks it in one call, and the note keeps what you still need. One warning until it shrinks.]` |
| Evicts | At the next request still over 0.85. A request already past the whole budget evicts at once. |
| Evicts down to | 0.50 of the budget |

Past 60k tokens, or half the window when that is smaller, every tool result says how full the window is: `context 95k of 180k`.

Order:

1. Finished turns go first, oldest first. Each goes whole.
2. If that is not enough, the running turn is thinned: every round but its newest 8, and more while the window is still over. A thinned round keeps its call. Its tool result, if over 600 characters, keeps at most its first 300 and a line `[thinned from N characters; (getf (recall-entry S) :text) reads it whole]`. Every round the turn holds then loses its reasoning.
3. If that is still not enough, the running turn sheds its oldest rounds.

The running turn keeps its user message and its newest round. It is never evicted whole.

Nothing summarizes evicted history except the agent. Its notes ride the stub, and the log keeps every word.

The eviction boundary only moves forward. An undo does not bring evicted turns back into the window.

## Stub

A stub is a system message that stands where the evicted history was.

Whole turns:

```lisp
[history evicted: seq A–B · N turns · defined: NAMES · watching: VALUES · recall: (recall-log :match "text" :before B+1)]
```

Rounds of the running turn:

```lisp
[turn history evicted: N rounds · seq A–B · defined: NAMES · watching: VALUES · recall: (recall-log :match "text" :after A-1 :before B+1)]
```

A notes block may follow on the next lines:

```lisp
[the evicted snippets noted and judged, oldest first; (recall-entry seq) reads one whole
 seq N · NOTE
 seq N · NOTE]
```

A whole-turn stub may carry two more blocks. `[evicted in N blocks, oldest first; ...]` lists each eviction's seq range, at most 12 lines. `[your own notes in the evicted turns, oldest first]` carries the notes the agent wrote into its context: the newest, then older ones while 6,000 characters hold them.

| Part | Meaning |
| --- | --- |
| `seq A–B` | The log positions that left the window. `recall-log` and `recall-entry` take the same numbers. |
| `defined:` | Definitions the evicted rounds recorded. Shown only when there are any. |
| `watching:` | The last values of watched cells. Shown only when there are any. |
| Notes block | One line per evicted cell that opened with a `;;` note. |

| Limit | Value |
| --- | --- |
| Names in `defined:` or `watching:` | 24, then `+N more` |
| Note lines | The newest 100, then `+N earlier` |
| Note line length | 320 characters |

Write a `;;` line at the top of a cell. That line survives eviction.

## /evict

`/evict [percent | through TURN]` forces an eviction. `through TURN` drops every retained turn up to and including that turn id. `/context history` lists the turns and runs it.

| Fact | Value |
| --- | --- |
| Alias | `/compact` |
| `percent` | 1 to 100. `40` and `40%` both work. |
| Default | 50 |
| Drops | The oldest whole turns, until at least that share of the retained history is gone. |
| Keeps | The newest turn, always. |

## Recall

The agent reads evicted history back from the log with three forms.

<Recording />

```lisp
(recall-log :match "text" :before 1200 :limit 10)
(recall-entry 1184)
(recall-search "deploy script")
```

### recall-log

Scans one session's log. Returns clipped rows, oldest first.

| Keyword | Default | Does |
| --- | --- | --- |
| `:match` | none | SQL LIKE over the event payload, the message's thinking left out. `%` and `_` are wildcards. ASCII case is ignored. |
| `:kinds` | input, assistant answer, tool call, tool result | One event kind or a list of kinds. |
| `:before` | none | Only rows with a `:seq` below this number. |
| `:after` | none | Only rows with a `:seq` above this number. |
| `:limit` | 20 | Maximum rows. |
| `:clip` | 200 | Characters kept per body. |
| `:session-id` | The current session | Another session to read. |

Each row carries `:seq`, `:at` (UTC time) and `:kind`. A tool result also carries `:duration-ms`. No row carries the model's thinking.

When more rows match than `:limit`, the newest rows are returned. The first element is then `(:matched N :showing M)`. Page older with `:before` set to the oldest `:seq` returned.

The scan includes the sessions this one was forked from, and turns hidden by an undo.

### recall-entry

`(recall-entry seq)` returns the one event at `seq` with its whole body. It returns `NIL` when no event holds that number.

### recall-search

`(recall-search query)` searches every session.

| Keyword | Default | Does |
| --- | --- | --- |
| `:kinds` | Same as `recall-log` | Event kinds to search. |
| `:limit` | 60 | Maximum rows. |
| `:window` | 220 | Characters of text around the match. |
| `:lead` | 32 | Characters of that text before the match. |

The query is split on spaces. Every word must appear. Words are literal: `%` and `_` match themselves. An empty query is an error.

Rows come newest first. Each carries `:session-id`, `:title`, `:seq` and a `:text` snippet.

## Checkpoints

Every turn is a checkpoint on the session tree.

| Command | Does |
| --- | --- |
| `/tree` | Opens the session tree. Continue from a turn, or rewind to it. Alias `/checkpoints`. |
| `/undo` | Rewinds the last turn. |
| `/redo` | Returns to the branch the last rewind left. |
| `/fork` | Forks a new session at the current head. |

A rewind adds a head move to the log. Nothing is deleted. Abandoned branches stay reachable.

In the shell, `/undo` also restores files by default. See [Sessions](/sessions).
