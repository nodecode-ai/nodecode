---
title: Self-policy
summary: "Let the agent write its own rules, identity and system prompt, with every edit a git commit, while you keep the switch and the fixed rules."
---

With `policy.self` on, the agent writes its own `AGENTS.md`, `SOUL.md` and system prompt. It edits them like any other file, with nothing to ask and nothing to wait for, and an edit binds from its next request. Every edit is a git commit you can read and revert. You keep the switch and the fixed rules. The mode is off by default, and off is exactly how Nodecode behaved before it.

{/* source: src/engine/policy.lisp */}
## Turn it on

Edit `~/.nodecode/config.jsonc` by hand:

```jsonc
"policy": {
  "self": true,
  // optional: where the history of the agent's edits is pushed
  "record": "git@github.com:you/agent-policy.git"
}
```

The agent cannot set `policy` itself, in either mode: `config-set` refuses the member to a tool call. Turning the mode on is your hand, never its own.

To turn it off, set `"self": false` or remove it. The store stays on disk, nothing in it binds, and your files are read as before.

## Off and on

| | Off (default) | On |
| --- | --- | --- |
| Your `AGENTS.md` in the home | `operator-rules`: your rules | The charter: your fixed rules, which outrank the agent's and which it cannot edit |
| The agent's own rules | None | `AGENTS.md` in the store, as the `agent-rules` section, labelled its own |
| Identity | `SOUL.md` from the channel's `soul_file`, chat only | `SOUL.md` in the store, in chat and in the terminal |
| System prompt | The shipped one | `SYSTEM.md` in the store when the agent writes one, else the shipped one |
| Who changes them | You, by hand | The agent, by editing the files |
| History | None | Every edit is a commit on the store's `adopted` branch |
| Record off the box | None | `adopted` pushed to `policy/adopted` on `policy.record`, never forced |

## How an edit binds

The store is `~/.nodecode/policy/`, a git repository of its own on the branch `adopted`. Its files are the policy:

| File | What it is |
| --- | --- |
| `AGENTS.md` | The agent's own rules |
| `SOUL.md` | Its identity. A new store starts from your `SOUL.md`. |
| `SYSTEM.md` | Its system prompt, the shipped one while the file is absent |
| `SYSTEM.shipped` | The shipped prompt `SYSTEM.md` was written against, kept by the store |

The agent edits a file with `edit`, `write-file` or `sh`. Before each request reads the policy, whatever changed on disk is committed, with a message naming the files, and the request carries that commit. So an edit binds from the next request, and no text binds that the history does not hold. `(policy-adopt FILES MESSAGE)` writes and commits in one step, with a message of the agent's own.

Every session is told where its policy lives and which commit it read, so the agent knows the files are its own to change.

To undo an edit, revert it in the store: `git -C ~/.nodecode/policy revert <commit>`. The next request reads the reverted text.

When a release ships a new system prompt while the agent runs its own, a standing notice `policy-prompt` says so, until the agent edits `SYSTEM.md` again. Its prompt is never replaced behind its back.

## Fixed rules

With the mode on, the agent's own verbs refuse to write the fixed rules when a tool call runs them. Your own edits, from a shell's `/config`, a settings page or a text editor, are no tool call and pass.

| Fixed rule | What a tool call is refused |
| --- | --- |
| The charter | `edit` or `write-file` of the home `AGENTS.md`, through a link too, or creating one where there was none |
| The config | `edit` or `write-file` of `config.jsonc` as a whole. Other members stay the agent's to set with `config-set`. |
| The switch | `config-set` of `policy`, in either mode |
| Who the operator is | `config-set` of any channel's `owner` |
| The guard | `config-set` of `guard`, or a `cells` list without `nodecode-guard` |
| The history | `edit` or `write-file` under `~/.nodecode/policy/.git/` |

## The record

When `policy.record` names a git remote, every commit the store makes is pushed to `refs/heads/policy/adopted` there, in the background, so a request never waits on the network. The push is never forced. If the history on the box was rewritten, the remote refuses the push, and a standing notice `policy record` says so until a push lands.

On the remote:

- Protect `policy/adopted`: no force-push, no deletion, and the rule applies to admins too. Without that, the record is only as safe as the box.
- The record's commits carry the store's git identity. Set `user.name` and `user.email` in the store to the account the remote's rules allow.

## What this does not protect

The agent owns its own process. `sh` can write any file the agent's user can, and a redefinition lifts any check written inside the program, the kernel's included, since `unlock-floor` lets the agent lower its own floor by design. The fixed rules above are a tripwire: no turn crosses one by accident, and one that tries is told why.

Nothing reviews an edit before it binds. What shows an edit afterwards is the history, and off the box, the record a rewritten history cannot replace. What blocks the effects you cannot undo is step 0.

## Step 0, before you turn it on

| Step | Why |
| --- | --- |
| Push with a token that has no admin rights and no Workflows permission | An admin token merges past required checks and changes branch protection back |
| Turn on branch protection with admins included (`enforce_admins`) | Otherwise the protection does not apply to the account the agent pushes as |
| Remove any admin login from the box: a `gh` login, `GH_TOKEN` | The agent reads every file its user can |
| Set a spending cap at each model provider | Nodecode has no spending cap of its own |
| Keep keys off the box, or make `sudo` ask for a password | With passwordless `sudo`, no user on the box keeps a key from the agent |
